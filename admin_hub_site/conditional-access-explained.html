How Conditional Access decides

What happens between entering a password and getting a token when Conditional Access policies are in place.

Read the steps as text
  1. Sign in. The user provides the first factor, usually a password.
  2. Risk check. Entra ID asks Identity Protection how risky this sign-in and this user are. This needs Entra ID P2.
  3. Risk level. The answer is a risk level such as low, medium or high, based on signals like unfamiliar locations or leaked credentials.
  4. Device check. For policies that need a managed device, Entra ID checks the device state with Intune.
  5. Compliance state. Intune reports whether the device is compliant.
  6. Evaluate policies. Entra ID passes all signals to Conditional Access: user or group, app, location, device platform and state, client app and risk.
  7. Decision. All matching policies are combined. The result is block, or grant with requirements such as MFA or a compliant device. A block ends with the error AADSTS53003.
  8. MFA, then tokens. The user completes what is required and Entra ID issues the tokens. If the result was a block, the user sees an error instead.

Good to know

  • Use report-only mode to test a new policy before enforcing it, and check the sign-in logs to see which policy applied.
  • All matching policies apply together, and a block always wins over a grant.
  • Keep emergency access accounts out of the policies, but monitor them.
